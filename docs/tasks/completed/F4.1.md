## Contrato técnico congelado

1. Existe um único endereço canônico: `.harness/state/structural-index/snapshots/<commit_sha>.json`, em
   que `commit_sha` é hexadecimal lowercase completo de 40 caracteres e corresponde a um commit
   comprovado por `git rev-parse --verify` no repositório consumidor.
2. `HEAD`, `HEAD~1` ou outra revisão podem ser entrada transitória para resolução Git, mas nunca nome,
   identidade ou campo persistido. Identidade inválida ou Git indisponível falha explicitamente.
3. O documento possui schema fechado e versionado: `schema_version`, `commit_sha`, `status`, `digest`
   e `symbols`. Somente status `ready` pode ser persistido/servido por este gate.
4. Cada símbolo usa um único schema fechado: `kind`, `name`, `qualified_name`, `path`, `line_start` e
   `line_end`. Strings soltas, campos extras, path absoluto/traversal, linhas inválidas e tipos coercíveis
   são recusados.
5. `digest` é `sha256:` do JSON canônico de todos os campos de conteúdo, excluído apenas o próprio
   digest. O loader revalida schema, SHA solicitado, status, digest e representação canônica antes de servir.
6. A publicação é atômica no mesmo diretório (`flush`, `fsync`, `os.replace`; fsync do diretório quando
   suportado). Regravação idempotente do mesmo conteúdo é aceita; conteúdo divergente para o mesmo SHA
   é conflito de integridade e nunca sobrescreve o snapshot existente.
7. `CodebaseMemoryAdapter` resolve a revisão para SHA real e serve somente snapshot íntegro existente.
   Ausência não cria dados, não inventa símbolos e falha explicitamente até a F4.2 fornecer o indexador.
8. `ContextAssembler` usa a mesma resolução e o mesmo `SnapshotManager`; arquivo ausente ou inválido
   não vira contexto vazio sintético. O score baseado em evidência continua reservado à F4.3.
9. `harness index` deixa de declarar atualização simulada: nesta fase ele somente valida/carrega snapshot
   existente ou apresenta erro explícito. Criação por AST e integração MCP continuam fora do escopo.
