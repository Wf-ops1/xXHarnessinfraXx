## Problema comprovado

| Evidência reproduzível | Resultado observado |
|---|---|
| `.\.venv\Scripts\python.exe -c "... SerenaAdapter().edit_file_semantic(...) ..."` | `{'result': True, 'exists': True, 'size': 0}`: sucesso declarado, arquivo ausente criado vazio e nenhuma mudança aplicada |
| `src/ai_engineering_harness/tools/adapters/serena.py` | `edit_file_semantic()` executa somente `mkdir`/`touch` e retorna `True`; não há transporte, handshake, discovery, capability ou efeito validado |
| `ToolRouter(allowed_tools=(...), registrations={})` e regressões F3.C2 | o registry operacional padrão permanece vazio; capabilities declaradas não possuem handlers de leitura/edição |
| `src/ai_engineering_harness/tools/adapters/git.py` | usa a API de shell string que a F3.5 tornou fail-closed e ainda contém SHA sintético `uncommitted` |
| README e plano F3.8 | exigem `read_file`, `list_files`, `search_text`, `apply_patch`, `run_command`, Git controlado e Serena MCP real ou fallback local explícito |

O caminho atual consegue afirmar uma edição inexistente e criar um artefato vazio fora de qualquer
contrato de patch. Não existe factory opt-in que ligue as primitivas já promovidas de path guard,
worktree e terminal ao `ToolRouter`. A F3.8 deve entregar essa superfície como primitiva operacional
injetável sem antecipar a ligação automática do lifecycle, a promoção Git ou uma disponibilidade MCP
que não tenha sido observada.

## Dependências revalidadas

1. F3.4 fornece `PathGuard` fail-closed com raiz explícita, resolução canônica, bloqueio de travessia,
   escrita em `.git` e limites de leitura/escrita.
2. F3.6 fornece `ProvisionedWorktree` com `PathGuard` cuja raiz é o worktree Git externo validado. A
   factory F3.8 recebe esse guard ou o provisionado explicitamente; nunca infere raiz por `cwd`.
3. F3.5 fornece `TerminalAdapter` por `argv`, executável absoluto autorizado, ambiente seletivo,
   timeout da árvore, saída limitada e redigida. F3.8 somente o adapta ao schema JSON da tool.
4. F3.C2 fornece `ToolRouter`, deny-wins, preflight do batch e write-ahead/outcome durável no tool loop.
   A F3.8 adiciona registrations opt-in; não relaxa policy nem o recorder obrigatório.
5. DEC-013 exige F3.4 + F3.6 antes da edição. DEC-014 exige novo PR administrativo somente depois de
   eventual merge/CI desta implementação; ela não autoriza publicação ou merge agora.
6. O SDK oficial MCP suporta cliente stdio e Streamable HTTP; Serena documenta lançamento por comando
   ou servidor HTTP. A dependência será `mcp>=1.26,<2`, compatível com o protocolo usado pela linha
   Serena 1.x e sem implementar JSON-RPC próprio.

## Contrato técnico congelado

1. `LocalEditingAdapter` exige `PathGuard` explícito e oferece `read_file`, `list_files`, `search_text`
   e `apply_patch`; nenhum método aceita raiz ou `cwd` implícito.
2. Leitura aceita somente arquivo regular UTF-8 estrito já existente, revalida o guard imediatamente
   antes do I/O e devolve path relativo, conteúdo e SHA-256 reais dentro do limite F3.4.
3. Listagem aceita somente diretório existente confinado, não percorre symlink para fora, possui
   profundidade e número máximo de entradas positivos, ordenação determinística e paths relativos.
4. Busca é literal e UTF-8, limitada por arquivos/resultados/bytes, percorre somente os paths que o
   guard revalidar e devolve arquivo, linha, coluna e trecho limitados; erro não vira lista vazia.
5. `apply_patch` aceita um único target e um patch unified-diff estrito. Multi-arquivo, rename, delete,
   binário, hunk malformado, contexto divergente, newline ambíguo ou trailing data falham tipados.
6. Arquivo existente exige o `expected_sha256` exato; criação exige ausência comprovada, digest nulo,
   parent existente/confinado e conteúdo não vazio. Patch sem mudança é erro, nunca sucesso.
7. A escrita verifica tamanho, proíbe `.git`, revalida target/parent imediatamente antes do efeito,
   publica por arquivo temporário no mesmo diretório + `fsync` + `os.replace` e devolve digest/path
   reais. Nenhum diretório é criado implicitamente.
8. `run_command` somente converte payload tipado em `CommandRequest` e chama um `TerminalAdapter`
   injetado. Não há shell string, resolução por PATH, herança de ambiente ou bypass do guard.
9. As operações Git deste gate são somente `git_status` e `git_diff`, por argv estático através do
   mesmo terminal seguro. Commit, add, checkout, reset, clean, branch, worktree, cherry-pick, revert,
   push e SHA fallback pertencem a F3.7/F6 e permanecem proibidos.
10. `SerenaAdapter` não possui endpoint default nem fallback silencioso. Ele recebe uma configuração
    explícita stdio ou Streamable HTTP, timeout finito, `PathGuard` do worktree e allowlist fixa de
    ferramentas semânticas de edição.
11. No stdio, o executável deve ser absoluto/existente, argumentos são argv sem shell e o projeto
    autorizado é fornecido explicitamente. No HTTP, a sessão deve inicializar, descobrir capabilities,
    ativar a raiz exata e comprovar o projeto ativo antes de qualquer edição.
12. Somente `replace_symbol_body`, `insert_before_symbol`, `insert_after_symbol` e `replace_content`
    podem ser chamados por `serena_edit`. `relative_path` é validado/injetado pelo adapter, não aceito
    duplicado dentro dos argumentos do modelo.
13. Antes e depois do call MCP, o arquivo-alvo é revalidado. Resultado MCP com erro, conexão ausente,
    capability faltante, raiz divergente, arquivo inalterado ou efeito fora do limite falha tipado e
    nunca retorna saudável/sucesso.
14. A factory opt-in registra schemas JSON exatos para as oito tools deste gate. Registration ausente
    continua produzindo `ToolUnavailableError`; policy compilada/deny-wins continua soberana.
15. O adapter local é fallback somente quando o chamador o selecionar explicitamente. Falha Serena
    não troca automaticamente de backend nem reaplica uma edição por outro caminho.
16. Nenhuma configuração default, grafo, CLI ou lifecycle passa a executar essas tools neste gate. A
    entrega é injetável/testável; sua ligação automática exige gate próprio para não misturar workspace,
    executor, configuração efetiva e promoção.

## Rollback

### Gatilhos

- retorno positivo sem mudança/digest real, patch parcial ou conteúdo/contexto divergente aceito;
- escape por path/symlink, escrita em `.git`, excesso de limite ou diretório implícito ocorrer;
- shell, PATH, ambiente herdado, Git mutável ou checkout original receber efeito;
- Serena declarar saúde sem initialize/discovery/root/capability, mudar arquivo fora da raiz ou acionar
  fallback local automaticamente;
- dependência não oficial/adicional, configuração default, lifecycle, CLI, policy, schema ou arquivo
  proibido tornar-se necessário;
- qualquer teste, quality gate, pacote, lock ou auditoria de escopo falhar.

### Procedimento não destrutivo

Parar e preservar saídas, temporários e diff para diagnóstico. Antes de commit, inverter somente os
hunks F3.8 com `apply_patch`. Depois de commit, usar `git revert` nos commits exclusivos desta branch;
nunca usar reset destrutivo, clean, checkout amplo ou sobrescrever trabalho do usuário. Se a correção
exigir ampliar a allowlist/efeito/dependência/critério, registrar R1 neste dossiê, recongelar e criar
novo checkpoint antes de retomar.

### Verificação pós-rollback

`git diff --check`, suíte documental, testes F3.4/F3.5/F3.6/tool-loop e suíte integral devem retornar
ao baseline verde. A reprodução do `SerenaAdapter` sintético pode voltar a existir somente se o gate
for formalmente abandonado; nesse caso o painel deve declarar `BLOCKED`, nunca sucesso.
