## Contrato técnico congelado

1. `ExternalWorktreeManager` exige `project_root` explícito, existente e igual à raiz canônica
   retornada por `git rev-parse --show-toplevel`; subdiretório, não repositório e bare repo falham.
2. O checkout original deve estar em branch simbólica e com `git status --porcelain=v1
   --untracked-files=all` vazio antes de qualquer referência ou worktree ser criado.
3. `execution_id` e `project_id` aceitam somente identificadores limitados e sem separador/traversal;
   a branch calculada é exatamente `harness/<execution_id>` e passa por `git check-ref-format`.
4. O manager captura `HEAD^{commit}` como SHA-base completo e a branch original. Um SHA esperado
   opcional funciona somente como precondição e mismatch falha antes do efeito.
5. A base externa é explícita/injetável para testes, canônica e fora do repositório original. O destino
   da execução e a referência não podem existir; colisão falha sem sobrescrever bytes ou branch.
6. A criação usa `git worktree add -b <branch> <external_path> <base_sha>` por lista de
   argumentos, `shell=False`, timeout finito e captura de saída; nunca usa shell string.
7. Depois do comando, o manager valida que o destino é a raiz Git esperada, que `HEAD` coincide com o
   SHA-base e que a branch ativa coincide com `harness/<execution_id>`.
8. A referência tipada é publicada atomicamente em
   `.harness/state/worktree-references/<execution_id>.json`, com schema, IDs, raiz, branch original,
   branch do worktree, SHA-base/HEAD, estado e horários. Escrita preparatória ocorre antes do efeito;
   falha controlada nunca vira `ACTIVE`.
9. O retorno `ProvisionedWorktree` contém a referência validada e um `PathGuard` cuja
   `authorized_root` é exatamente a raiz canônica do worktree. Somente essa raiz pode ser entregue a
   consumidores futuros.
10. Reabertura por referência valida schema/estado, raiz Git, branch e SHA antes de reconstruir o
    `PathGuard`; conteúdo ausente, adulterado ou ambíguo falha fechado.
11. Remoção ocorre somente por `cleanup_worktree(execution_id)`, usa `git worktree remove <path>` sem
    `--force`, preserva a branch `harness/*` e publica estado `REMOVED`; worktree sujo bloqueia cleanup.
12. Todos os erros são tipados e encadeiam a causa sem retornar sucesso sintético. O checkout original
    não recebe edição de produto, commit, cherry-pick, reset, clean ou exclusão de branch.
13. Este gate não registra capability, não altera tool loop/terminal/Serena/promoção e não promete que
    tools já são executadas; apenas entrega o contexto seguro que F3.5/F3.8 deverão consumir.

## Rollback

### Gatilhos

- diretório comum ser aceito como worktree ou HEAD/branch/raiz divergirem da referência;
- projeto inválido, subdiretório, checkout sujo/detached ou SHA esperado divergente produzir efeito;
- comando Git usar shell, não possuir timeout ou aceitar metacaracter como sintaxe;
- path interno ao checkout, colisão, referência adulterada ou escrita parcial ser aceita;
- cleanup implícito/forçado, exclusão de branch ou alteração do checkout original ocorrer;
- solução exigir runtime, tool, adapter, CLI, promoção, dependência ou arquivo fora do congelado;
- qualquer aceite, regressão, quality, package ou auditoria de escopo falhar.

### Procedimento não destrutivo

Parar e preservar referência, worktree e saídas para diagnóstico. Antes de commit, inverter somente
hunks F3.6 com `apply_patch`. Depois de commit, usar `git revert` nos commits exclusivos desta branch.
Worktree de teste fica sob diretório temporário; worktree real eventualmente criado só pode ser
removido pelo cleanup explícito não forçado. Nunca usar reset/clean/force-push nem descartar branch.

### Verificação pós-rollback

Confirmar status, HEAD/checkpoint, `git diff --check` e zero diff de produto contra
`checkpoint/f3.6-ready`; repetir documentação, compatibilidade, regressão, quality e package.

### Resultado implementado

- `ExternalWorktreeManager` valida Git disponível, raiz exata do repositório, branch original anexada,

  publicação atômica com flush/fsync/replace; reabertura revalida owner, path, branch, SHA e horários.
- cleanup é API explícita, sem `--force`, recusa alterações e preserva a branch `harness/*`; o
  checkout original mantém branch, HEAD e conteúdo versionado intactos.
- o falso positivo legado que aceitava `tmp_path` sem Git foi removido. Nenhum terminal, adapter,
  registration, tool loop, runtime, candidate commit ou promoção foi integrado.
