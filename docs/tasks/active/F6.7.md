## Contrato técnico congelado

1. `execute_transaction(tx_id, new_ki, *, commit_sha)` exige identificador seguro, KI JSON finita
   com `id` canônico e SHA completo que exista como commit no repositório Git.
2. O índice persistido é JSON canônico content-addressed; `index_digest` é SHA-256 recalculado na
   execução, no recovery e ao carregar o ponteiro corrente.
3. Um lock cross-processo global serializa qualquer alteração knowledge. Cada aquisição avança um
   fencing token durável; `PREPARED`, pointer e resultado terminal registram o token observado.
4. A ordem write-ahead é: staging íntegro → `PREPARED` atômico → snapshot imutável → pointer swap
   atômico condicionado ao predecessor → `COMMITTED` atômico. Nenhuma etapa posterior pode ser
   inferida apenas pela intenção anterior.
5. Recovery aceita somente um `PREPARED` não resolvido. Ele valida journal, SHA Git, digest, staging
   ou snapshot e pointer atual. Pode concluir a mesma transação, abortá-la antes do pointer quando a
   falta/divergência é comprovada, ou falhar fechado se o efeito corrente é ambíguo.
6. Pointer já publicado e idêntico permite somente completar o journal; pointer avançado por outra
   transação nunca é sobrescrito. Transação `COMMITTED` repetida é idempotente somente para o mesmo
   SHA e a mesma KI.
7. Cada novo snapshot incorpora todos os KIs do snapshot corrente e substitui apenas o mesmo `id`;
   atualizar `current.json` não pode perder KIs anteriores.
8. Pointer legado pode ser migrado somente se seu staging antigo existir e validar. Journal legado
   `PREPARED` sem metadados/staging é marcado `ABORTED`, nunca `COMMITTED`.
9. Retenção é explícita, limitada a snapshots comprovadamente `COMMITTED`, preserva sempre o atual e
   nunca remove staging abortado/corrompido ou evidência ambígua.
10. Erros de configuração, integridade, conflito, recovery e escrita são tipados. Nenhum retorno
    sintético, fallback permissivo, cleanup destrutivo ou `shell=True` é permitido.

## Critérios de aceite congelados

1. Sucesso prova staging, `PREPARED`, snapshot, pointer e `COMMITTED` com SHA existente, digest
   recalculável e fencing monotônico.
2. Duas transações preservam os KIs anteriores; atualizar o mesmo ID substitui somente esse item.
3. Fault injection antes/depois de `PREPARED`, publicação do snapshot, pointer swap e append terminal
   prova recovery idempotente sem segundo pointer, perda de KI ou falso commit.
4. Staging ausente/corrompido antes do pointer resulta `ABORTED`; pointer publicado com snapshot
   ausente/corrompido ou identidade divergente falha fechado e preserva bytes.
5. Concorrência cross-processo é serializada; fencing cresce e token obsoleto não publica pointer.
6. SHA inválido/inexistente, digest adulterado, journal inválido, tx reutilizada com outro conteúdo e
   pointer divergente falham antes de sobrescrever estado válido.
7. Retenção remove somente snapshots antigos comprovadamente committed, preserva o atual e o snapshot
   corrente continua contendo todos os KIs.
8. A caracterização F6.6 deixa de aceitar `RECOVERED_tx-missing`: o mesmo caso termina abortado ou
   bloqueado, sem `COMMITTED` e sem pointer.
